# wb-staged-claim-guard

Плагин Discourse: не даёт занять теневую учётку служебного адреса компании регистрацией, приглашением
или входом.

## Зачем

**22.10.2026 проверено на тестовом портале.** Любой, кто заполнит форму регистрации с адресом
`info@wirenboard.com`, сразу — ещё до подтверждения по ссылке — превращает теневую учётку этого адреса
в свою обычную неподтверждённую: имя, пароль и язык становятся его, уведомления стираются. Механизм — в
ядре:

```ruby
user = User.where(staged: true).with_email(new_user_params[:email].strip.downcase).first

if user
  user.active = false
  user.unstage!
end
```

Подтвердить захват посторонний не может — письмо со ссылкой уходит в ящик info@. Но с этой минуты
портал отбрасывает всю почту от info@ как от неподтверждённой учётки:

```ruby
raise InactiveUserError if !user.active && !user.staged
```

А через info@ на портал идут ответы менеджеров из Zammad (около 100 писем в месяц) и приглашения Wiren
Board Cloud. Заблокировать сам адрес нельзя: блок-лист отбрасывает и письма от него.

Запретить захват всем теневым учёткам тоже нельзя. Это штатный путь клиентов: кто сначала писал
письмом, потом регистрируется с тем же адресом и получает свою переписку — так на портале появилась
391 учётка, 90 из них за последний год.

## Как работает

- **Форма регистрации** (`UsersController#create`). Если адрес принадлежит теневой учётке на
  защищённом домене, регистрация получает понятный отказ, учётка не трогается, в ящик ничего не уходит.
  Защита от ботов (honeypot) срабатывает раньше, как обычно.
- **Все остальные пути**, которыми ядро снимает «теневость», перехвачены в `User#unstage!`:
  ссылка-приглашение (её может сделать любой, кому разрешено приглашать, и указать при входе чужой
  адрес), вход по коду из письма, DiscourseConnect и сам вход. Для защищённой учётки `unstage!`
  отказывает исключением валидации; контроллер приглашений показывает текст отказа (412) вместо падения.
- Каждый отказ пишется в `production.log` и в **журнал действий персонала**
  (`wb_staged_claim_refused`, с адресом и IP).
- Защищаются только **уже существующие теневые учётки**. Новые регистрации на этих доменах и теневые
  учётки клиентов живут как раньше.

## Настройки (Админка → Настройки → Плагины)

| настройка | по умолчанию | смысл |
|---|---|---|
| `wb_staged_claim_guard_enabled` | включено | выключать только для осознанного перевода служебной учётки в обычную |
| `wb_staged_claim_guard_protected` | `wirenboard.com\|wirenboard.ru\|contactless.ru` | домен целиком; запись с `@` — ровно этот адрес |

Сотрудник, чей рабочий адрес уже есть на портале теневой учёткой, сам зарегистрироваться с ним не
сможет — такую учётку заводит администратор.

## Проверка

`spec/` — 14 примеров, зелёные на ядре прода (2026.8, `c9dd39f8`) и тестового портала (2026.7.1): разбор адресов из настройки; форма
регистрации — отказ для info@, клиент регистрируется как раньше, новая регистрация на домене компании
проходит, без предохранителя захват воспроизводится; ссылка-приглашение — отказ 412, без
предохранителя обход формы воспроизводится, клиент как раньше; сам `unstage!` — не стирает уведомления
и пишет в журнал.

## Связано

Сторож портала `wb-portal-watchdog` следит, что учётка info@ осталась теневой (проверка `info_staged`),
и умеет откатить захват — второй рубеж на случай, если плагин выключат.
